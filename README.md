# دليل الكفاءات الصحية لعائلة النتشة — المشروع التقني

تطبيق ويب عربي (RTL) مبني بـ **Next.js + Tailwind CSS + Supabase**، وفق وثيقة المتطلبات
[`دليل_الكفاءات_الصحية_لعائلة_النتشة_المواصفات_الشاملة.md`](./دليل_الكفاءات_الصحية_لعائلة_النتشة_المواصفات_الشاملة.md).

## هيكل المشروع

```
app/
  layout.tsx              التخطيط العام (RTL، الخطوط، العنوان)
  page.tsx                الصفحة الرئيسية
  (public)/
    directory/page.tsx    الصفحة العامة لدليل الكفاءات (تقرأ من View directory_public)
    join/page.tsx         نموذج طلب الانضمام (هيكل الخطوة الأولى)
    login/page.tsx        تسجيل الدخول برقم الهوية
  admin/
    layout.tsx            حماية /admin + التحقق من الدور (reviewer/admin)
    page.tsx               لوحة مؤشرات مبسطة
lib/supabase/
  client.ts               عميل Supabase لمكونات المتصفح
  server.ts               عميل Supabase لمكونات الخادم
proxy.ts                  تحديث الجلسة + إعادة توجيه /admin لغير المسجلين (اصطلاح Next.js 16 بديل middleware)
database/
  001_schema.sql           الجداول والعلاقات
  002_rls_policies.sql      سياسات الأمان (RLS)
  003_public_directory_view.sql   View العرض العام الآمن
  004_seed_reference_data.sql     بيانات مرجعية أولية
  README.md                 تفاصيل قرارات التصميم وطريقة التنفيذ
public/logo.png            الشعار الرسمي لمجلس عائلة النتشة
```

## خطوات التشغيل

### 1. المتطلبات

- **Node.js 20+** و npm — غير مثبّتين حاليًا على هذا الجهاز، يجب تثبيتهما أولًا من
  [nodejs.org](https://nodejs.org).
- حساب [Supabase](https://supabase.com) (مجاني للبدء).

### 2. تثبيت الحزم

```bash
npm install
```

### 3. إعداد Supabase

1. أنشئ مشروعًا جديدًا في Supabase (يُفضّل أن يكون تحت حساب مؤسسي للمجلس وليس حسابًا شخصيًا — القسم 62).
2. نفّذ ملفات `database/*.sql` بالترتيب المذكور في `database/README.md`.
3. انسخ `.env.example` باسم `.env.local` واملأ القيم من **Project Settings → API**.
4. **مهم:** من **Authentication → Sign In / Providers → Email**، عطّل **Confirm email**. النظام يُنشئ لكل مستخدم بريدًا داخليًا مصطنعًا (القسم 14) لا يستقبل رسائل فعلية، فبقاء هذا الخيار مفعّلاً يمنع أي حساب جديد من الحصول على جلسة دخول بعد التسجيل. الحماية الفعلية للنظام لا تعتمد على تأكيد البريد أصلاً، بل على المراجعة اليدوية قبل النشر (القسم 20-21).

### 4. تشغيل بيئة التطوير

```bash
npm run dev
```

يفتح الموقع على `http://localhost:3000`.

### 5. النشر

- **الكود:** يُرفع إلى مستودع **GitHub خاص** مملوك للمجلس (القسم 45).
- **الاستضافة:** ربط المستودع بـ **Vercel** ونسخ متغيرات البيئة نفسها هناك (القسم 46).

## حالة التنفيذ الحالية (نقطة انطلاق، وليست نسخة جاهزة للإنتاج)

هذا الهيكل يغطي دورة العمل الكاملة فعليًا على قاعدة بيانات حقيقية: تسجيل دخول
برقم الهوية، نموذج "طلب انضمام" (4 خطوات) يكتب في كل الجداول المعنية، شاشة
مراجعة واعتماد ونشر في لوحة الإدارة (القسم 21)، الدليل العام يعرض المعتمد
والمنشور فقط، و**"ملفي الشخصي"** (القسم 33) حيث يستطيع صاحب الحساب رؤية حالته
وتعديل بياناته — تعديلات بسيطة تُطبَّق فورًا، وتعديلات جوهرية (الاسم، التخصص،
المؤهل، جهة العمل، الترخيص) على ملف منشور مسبقًا تُرسَل كـ `change_requests`
بانتظار مراجعة الإدارة (القسم 34). كما تتوفر شاشات لإدارة البيانات المرجعية
(المجالات الصحية والتخصصات الرئيسية/الدقيقة، الفروع العائلية، الدول والمدن)
من لوحة الإدارة مباشرة دون الحاجة لكتابة SQL (القسم 7، 53، 54) — إضافة وتفعيل/
تعطيل فقط دون حذف، حفاظًا على السجلات المرتبطة.

> **تحديث:** جُمعت هذه الشاشات الثلاث (كانت روابط منفصلة في الشريط العلوي
> المزدحم أصلاً) تحت رابط واحد **"ثوابت النظام"** (`/admin/settings`)، بتبويب
> داخلي (`components/SettingsTabs.tsx`) يفصل بين التخصصات والفروع والدول
> والمدن دون تغيير أي من منطقها الداخلي — مجرد نقل مسارات
> (`/admin/specialties` → `/admin/settings/specialties`، وبالمثل للفروع
> والمواقع).

كما تعمل آلية **"نسيت كلمة
المرور"** الكاملة (القسم 36): طلب برقم الهوية والهاتف يُطابَق تلقائيًا مع
البيانات المسجلة، ثم شاشة في لوحة الإدارة يتحقق فيها المدير هاتفيًا من الشخص
قبل توليد كلمة مرور مؤقتة وتفعيلها فورًا (عبر دالة قاعدة بيانات محمية بدل
الاعتماد على بريد إلكتروني حقيقي غير متوفر أصلاً). وأصبحت شاشة **"طلبات
التعديل"** في لوحة الإدارة تعرض كل تعديل جوهري بانتظار المراجعة (قبل/بعد)
مع اعتماد يطبّقه فعليًا على الملف المنشور أو رفضه.

الشعار الرسمي (`public/logo.png`) يظهر الآن في هيدر وفوتر كل الصفحات العامة
(عبر `components/SiteHeader.tsx` و`SiteFooter.tsx` المطبَّقين تلقائيًا على
مجموعة `app/(public)`)، وكذلك في هيدر لوحة الإدارة و"ملفي الشخصي" — تطبيقًا
كاملاً للقسم 49.1.

> **إصلاح إتاحة الاستخدام على الهاتف:** فحص فعلي للموقع على أحجام الهاتف
> والتابلت والكمبيوتر (القسم 50) كشف أن روابط التنقل في الشريط العلوي كانت
> **تختفي بالكامل دون بديل** على شاشات الهاتف (`hidden sm:inline`)، تاركة
> فقط الشعار وزر الحساب — لا طريقة للوصول لدليل الكفاءات أو طلب الانضمام من
> الهيدر على الهاتف. عولج بإضافة قائمة همبرغر منسدلة
> (`components/MobileNav.tsx`، مكوّن عميل صغير) تظهر فقط تحت `sm`، وتحتوي كل
> روابط التنقل وزر الحساب، مع بقاء الشريط الأفقي الكامل كما هو على الشاشات
> الأكبر دون أي تغيير.

شاشة مراجعة الطلب تعرض أيضًا **تنبيه تشابه محتمل** (القسم 22): تطابق تام في
الهاتف/الواتساب، أو تشابه في الاسم عبر `pg_trgm` (`similarity() >= 0.35`)، مع
أي مسجل آخر — تنبيه فقط للمراجع، بلا أي دمج أو حذف تلقائي.

**رفع الصورة الشخصية** (القسم 15) يعمل فعليًا الآن عبر Supabase Storage
(دلو `profile-photos`، حد 5 ميغابايت، JPG/PNG فقط) — من نموذج طلب الانضمام
(الخطوة 2) ومن "ملفي الشخصي" لاحقًا، مع عرضها للمراجع في شاشة اعتماد الطلب
ليتحقق من ملاءمتها قبل النشر.

شاشة **"التقارير"** الجديدة في لوحة الإدارة (القسم 30) تعرض بطاقات عددية
(الإجمالي/بانتظار المراجعة/معتمد/منشور/مرفوض دائمًا على كل السجلات)، وجداول
تفصيلية قابلة للتصفية بنطاق (كل السجلات / المعتمد فقط / المنشور فقط، القسم 56):
التوزيع حسب المجال الصحي، الدولة (مع فصل داخل/خارج فلسطين)، المؤهل العلمي،
وسنوات الخبرة. **التصدير** (القسم 32) متاح بصيغتين: **CSV** (يفتح مباشرة في
Excel، ويشمل رقم الهوية لأنه تصدير إداري مقصور على admin فقط)، و**PDF** عبر
صفحة قابلة للطباعة (`/admin/reports/print`) يحفظها المتصفح كـ PDF مباشرة —
دون الحاجة لمكتبة توليد PDF منفصلة.

> **إعادة هيكلة لاحقة:** فُصل قسم التقارير السابق إلى شاشتين منفصلتين لهما
> تبويب علوي مشترك (`components/AdminSectionTabs.tsx`):
>
> - **`/admin/statistics` ("الإحصائيات")**: نفس التوزيعات المجمّعة أعلاه، بعرض
>   بصري أوضح (بطاقات ملونة حسب الحالة + أشرطة نسب مئوية لكل توزيع)، مع
>   إضافة توزيعين جديدين لم يكونا معروضين من قبل رغم توفر بياناتهما: **حسب
>   الفرع العائلي** و**حسب نوع مكان العمل**. زر واحد "تنزيل الإحصائيات
>   (CSV)" يُصدّر كل الجداول المجمّعة دفعة واحدة (`/admin/statistics/export`).
> - **`/admin/reports` ("التقارير")**: بيانات تفصيلية كاملة لكل شخص (وليس
>   أرقامًا مجمّعة) عبر أداة **فلاتر متعددة الاختيار** (Multi-select): الحالة،
>   الفرع العائلي، المجال الصحي، الدولة — يمكن اختيار أكثر من قيمة في كل
>   فلتر معًا (مثلاً أكثر من دولة وأكثر من حالة دفعة واحدة)، وتُبنى الفلاتر
>   كنموذج HTML عادي (GET) بلا حاجة لجافاسكريبت من جهة العميل. زر **"تصدير
>   CSV"** يُصدّر النتيجة المصفّاة تحديدًا كما تظهر على الشاشة
>   (`/admin/reports/export`، بنفس معايير الفلترة من رابط الصفحة).
>
> صفحة الطباعة القديمة (`/admin/reports/print`) و`PrintButton.tsx` حُذفتا
> لأن كلا القسمين الجديدين يعتمدان تصدير CSV فقط (بدل CSV+PDF)، بقرار صريح
> من مالك المشروع لتوحيد الصيغة وتبسيط الصيانة.

> **قرار متعمّد:** لم تُستخدم مكتبة `xlsx` (SheetJS) لتوليد ملفات `.xlsx` حقيقية
> لأن نسخة npm الحالية تحمل ثغرتين معروفتين بلا إصلاح متاح. بما أن CSV يُفتح في
> Excel مباشرة بنفس النتيجة العملية، اعتُمد كبديل أكثر أمانًا. يمكن إعادة النظر
> لاحقًا إذا توفّر إصلاح أو ظهرت حاجة فعلية لتنسيق `.xlsx` أصلي (تنسيق خلايا،
> عدة أوراق، إلخ).

صفحة **الدليل العام** أصبحت أكثر ديناميكية بعد مراجعة مواقع مشابهة: شريط
إحصاءات بأعداد متحركة (`components/AnimatedNumber.tsx`) يعكس العدد الحقيقي
دائمًا (وليس أرقامًا ثابتة)، وسوم تخصصات سريعة أعلى النتائج (أكثر 6 تخصصات
انتشارًا فعليًا، بالضغط عليها تُصفّي القائمة فورًا)، وشارة **"انضم حديثًا"**
تلقائية على أي ملف اعتُمد خلال آخر 30 يومًا — كل ذلك محسوب من البيانات
الفعلية دون أي إدخال يدوي.

**صفحة "الكفاءات الصحية بالأرقام" العامة** (`/stats`، القسم 31) تعرض إحصاءات
مجمّعة فقط (بلا بيانات شخصية): التوزيع حسب التخصص والدولة، وداخل/خارج فلسطين
— مصممة لتكون قابلة للمشاركة والفخر العائلي. كما أضيفت **أزرار مشاركة عبر
واتساب** (`components/WhatsAppShareButton.tsx`) **وفيسبوك**
(`components/FacebookShareButton.tsx`، عبر نافذة مشاركة فيسبوك الرسمية
`sharer.php`) جنبًا إلى جنب في الصفحة الرئيسية وكل ملف شخصي عام، تفعيلاً
لأقصر مسافة بين مشاهدة الدليل ودعوة أحد أفراد العائلة له.

> **إصلاح:** اكتُشف أن مشاركة رابط صفحة طبيب عبر فيسبوك كانت تنتهي بربط
> المنشور بالصفحة الرئيسية بدل صفحة الطبيب نفسها، بسبب غياب بيانات
> **Open Graph** (`og:url`, `og:title`, `og:image`) الخاصة بكل صفحة — كل
> الصفحات كانت ترث نفس بيانات `layout.tsx` العامة. عولج بإضافة `metadataBase`
> في `app/layout.tsx`، ودالة `generateMetadata` في صفحة الطبيب
> (`app/(public)/directory/[id]/page.tsx`) تُصدِّر عنوانًا ووصفًا ورابط
> `og:url` خاصًا بكل طبيب، مع صورته الشخصية إن وافق على عرضها وإلا الشعار
> الرسمي كصورة احتياطية. الصفحة الرئيسية غير متأثرة وتحتفظ ببياناتها كما هي.

**طلب حذف الحساب نهائيًا** (القسم 38) يعمل الآن أيضًا: من "ملفي الشخصي" يمكن
لصاحب الحساب طلب الحذف بعد تأكيد صريح، فيُخفى ملفه فورًا (حالة "موقوف")، ثم
تصل الإدارة إلى شاشة **"طلبات الحذف"** حيث يمكنها إما **الحذف النهائي** (يمسح
فعليًا بيانات الهوية/الاتصال/الملف/البيانات المهنية، ويقفل تسجيل الدخول
نهائيًا) أو **الرفض واستعادة الحساب** لحالته السابقة — احترازًا من طلب حذف
كيدي من حساب مخترق.

> **ملاحظتان صادقتان حول هذا التنفيذ:**
> 1. الوثيقة تذكر مهلة "خلال 30 يومًا" قبل الحذف الفعلي؛ نُفِّذ هنا **حذفًا
>    فوريًا عند تأكيد المدير يدويًا** بدل جدولة تلقائية (لا توجد بعد وظيفة
>    مجدولة/Cron في المشروع)، وهذا يفي بالغرض العملي لكنه ليس مطابقًا حرفيًا
>    لرقم المهلة.
> 2. لا يُحذف حساب Supabase Auth فعليًا (يتطلب Service Role Key الذي لم
>    نستخدمه عمدًا في هذا المشروع)؛ بدلاً من ذلك يُقفل الدخول نهائيًا بكلمة
>    مرور عشوائية طويلة لا يعرفها أحد — النتيجة العملية واحدة (لا يمكن الدخول
>    مطلقًا)، لكنه ليس حذفًا فعليًا لسجل المصادقة نفسه.

بهذا اكتملت كل عناصر قائمة الإصدار الأول (القسم 59) المذكورة أصلاً في هذا
الملف.

### تحسينات على الدليل العام (بعد مراجعة مواقع مشابهة كـ altibbi.com)

- **صفحة ملف عام فعلية** لكل شخص (`/directory/[id]`) لم تكن موجودة سابقًا —
  تعرض Breadcrumb كامل، بيانات الاتصال المسموح بها، ونبذة مهنية.
- **إخفاء الهاتف/الواتساب خلف زر "اضغط لإظهار الرقم"** (`components/RevealField.tsx`)

- **أيقونة افتراضية أنيقة** (`components/DirectoryAvatar.tsx`) بدل مربع فارغ
  عند غياب الصورة الشخصية.
- **شارة توثيق** ملاصقة للاسم (`components/VerifiedBadge.tsx`) في البطاقة
  وصفحة الملف.
- **قسم "كفاءات أخرى في نفس التخصص"** أسفل كل ملف شخصي، لتشجيع تصفح إضافي.

## تذييل الصفحات وسياسة الخصوصية

**التذييل** (`components/SiteFooter.tsx`) أصبح أكثر اكتمالاً: روابط سريعة
لأهم صفحات الموقع، شعار المجلس بحجم مصغّر مناسب لعنصر تذييل، وأيقونة **فيسبوك**
تربط مباشرة بصفحة المجلس الرسمية (facebook.com/natshehcouncil). تحته اسم
الجهة المشرفة "المجلس العائلي لعائلة النتشة — فلسطين، الخليل"، سطر حقوق نشر
بالسنة الحالية محسوبة تلقائيًا، وسطر اعتماد "تصميم وإعداد: د. أحمد عوني
النتشة". لا يوجد بعد رقم هاتف أو بريد إلكتروني رسمي للتذييل — سيُضافان عند
توفرهما.

> **تحديث:** أُعيد تنظيم التذييل بتخطيط احترافي متعدد الأعمدة (نمط شائع في
> المواقع العالمية) بدل الروابط المتفرقة أفقيًا: عمود للهوية والتواصل
> (الشعار + وصف قصير + أيقونة فيسبوك)، عمود "روابط سريعة" (يتضمن الآن رابط
> **الرئيسية** الذي كان مفقودًا)، وعمود "الحساب والخصوصية" (تسجيل الدخول
> وسياسة الخصوصية)، مع شريط سفلي منفصل لاسم الجهة المشرفة وحقوق النشر
> وسطر الاعتماد.

**صفحة سياسة الخصوصية والاستخدام** (`/privacy`) جديدة بالكامل، وتشرح بلغة
واضحة غير قانونية جامدة: من يشرف على الدليل، أنواع البيانات المجمّعة والغرض
منها، الفرق بين ما ينشر للعامة وما يبقى داخليًا فقط (القسم 36)، آلية المراجعة
قبل النشر، من يملك صلاحية الوصول للبيانات الكاملة، حق التعديل والحذف النهائي
للحساب، مدة الاحتفاظ بالبيانات، وسياسة عدم فهرسة الملفات الشخصية في محركات
البحث. رابطها مضاف في تذييل كل صفحة عامة، وكذلك كخانة إلزامية للموافقة عليها
ضمن نموذج طلب الانضمام (`app/(public)/join/page.tsx`).

## إضافات لاحقة بعد مراجعة الوثيقة

- **صفحة "عن الدليل"** (`/about`) — كانت مذكورة في القائمة الرئيسية بالوثيقة
  (القسم 11) دون أن تُبنى فعليًا؛ أُضيفت الآن بمحتوى مستقل عن رسالة الدليل
  وأهدافه والجهة المشرفة، ورُبطت من هيدر وفوتر كل الصفحات العامة.
- **دعم طلاب ومتدربي القطاع الصحي**: أصبح حقل "سنوات الخبرة" في نموذج طلب

  توضيحي وإضافة "طالب / متدرب" كمثال ضمن حقل المؤهل العلمي — تحقيقًا لهدف
  الدليل في توثيق الكفاءات الصاعدة لا العاملين فقط (القسم 4).
- **تقرير "المساهمة الصحية المستقبلية"** في لوحة التقارير (`lib/reports.ts`)
  يستثمر بيانات القسم 16 التي كانت تُجمع دون أي استخدام فعلي: يعرض توزيع

  التقارير ونسخة الطباعة/PDF.
- تحديث مرجعي في وثيقة المتطلبات نفسها لتطابق شارة التحقق **الزرقاء** المعتمدة
  فعليًا (بدل الأخضر المذكور ابتدائيًا في القسم 23.1).

## تحسين تسلسل أزرار الشريط العلوي

لوحظ أن زرّي "تسجيل الدخول" و"طلب انضمام" في الشريط العلوي (`components/SiteHeader.tsx`)
كانا يأخذان وزنًا بصريًا أكبر من رابط تصفح الدليل نفسه (نص عادي فقط)، بعكس
تسلسل الأولوية في الصفحة الرئيسية — ما قد يوحي للزائر بأن التسجيل مطلوب
لمجرد التصفح. أُعيد ترتيب الأولوية البصرية لتطابق الصفحة الرئيسية:

- **"تصفّح دليل الكفاءات"** — زر أساسي مملوء (بدل رابط نصي).
- **"انضمام كفاءة صحية جديدة"** — زر ثانوي بإطار (بدل "طلب انضمام").
- **"تسجيل دخول الكادر الصحي"** — رابط نصي بسيط (بدل زر مملوء بارز)، لتوضيح
  أنه مخصص لأعضاء مسجَّلين مسبقًا وليس خطوة عامة مطلوبة للتصفح.

نفس التسميات محدَّثة في التذييل والصفحة الرئيسية وصفحة "عن الدليل" للاتساق.

## تنقّل حر بين خطوات نموذج طلب الانضمام

لوحظ أن تبويب الخطوات الأربع أعلى نموذج `/join` كان مجرد مؤشر عرض غير قابل
للضغط، والانتقال من خطوة إلى التالية يتطلب إرسال الخطوة الحالية فعليًا —
والأخطر أن إرسال الخطوة الأولى **ينشئ حسابًا حقيقيًا** في قاعدة البيانات.
هذا يعني أن الشخص "يلتزم" فعليًا بإنشاء حساب قبل أن يرى حجم الخطوات
المتبقية، ما قد يثنيه عن البدء أصلاً خشية أن تكون الخطوات القادمة طويلة.

أصبحت عناوين الخطوات الأربع (`app/(public)/join/page.tsx`) قابلة للضغط
للتنقل الحر بينها في أي اتجاه، فيستطيع أي زائر استعراض كل الحقول المطلوبة
في النموذج كاملاً **دون تعبئة أي بيانات ودون إنشاء أي حساب** — الإرسال
الفعلي (وبالتالي إنشاء الحساب) يحدث فقط عند الضغط الصريح على زر "التالي"
في كل خطوة كما كان، فالتنقل للاستعراض لا يُنشئ أو يُعدّل أي سجل في قاعدة
البيانات.

## شاشة "المستخدمون" — إدارة حسابات الفريق (القسم 28)

كان إنشاء حساب مدير/مراجع جديد يتطلب تدخلاً يدويًا مباشرًا في قاعدة البيانات
(كما حصل مع تأسيس أول حساب مدير، القسم 62.1) دون أي واجهة لتكرار ذلك لاحقًا.
أُضيفت شاشة **"المستخدمون"** (`app/admin/users/page.tsx`) تتيح للمدير:

- **عرض** كل حسابات الفريق الحالية (مدير/مراجع) مع اسم كل حساب وبريده.
- **إنشاء حساب فريق جديد** — يختار المدير **الصلاحية أولاً** (مدير نظام أو
  مراجع)، ثم يُدخل يدويًا اسم الشخص، واسم المستخدم (بريد إلكتروني)، **وكلمة
  المرور نفسها** (بدل توليدها عشوائيًا كما كان سابقًا) — ليتحكم المدير
  بكلمة مرور يسهل عليه تذكرها أو إرسالها للشخص المعني مباشرة.
- **إلغاء صلاحية** أي حساب فريق (بإعادته إلى دور "applicant" العادي، فيفقد
  الوصول للوحة الإدارة فورًا دون حذف الحساب فعليًا) — مع منع المدير من إلغاء
  صلاحيته عن نفسه تفاديًا لقفل الوصول بالكامل عن غير قصد.

**ملاحظة تقنية:** لا يملك المشروع مفتاح `service_role` (قرار متعمّد منذ
البداية)، لذا لا يمكن استخدام واجهة Supabase Admin API لإنشاء المستخدمين
مباشرة. الحل المعتمد (`app/admin/users/actions.ts`): إنشاء الحساب عبر
`auth.signUp()` العادي باستخدام **عميل Supabase منفصل ومؤقت** (بمفتاح anon
فقط، بلا حفظ جلسة `persistSession: false`) حتى لا تتأثر جلسة تسجيل دخول
المدير الحالي أثناء العملية، ثم ربط الحساب الجديد بصلاحيته عبر الجلسة
الحقيقية للمدير — وهذا مسموح به لأن سياسة RLS "الإدارة تدير الحسابات"
(`for all using (is_admin())`) تمنح المدير أصلاً صلاحية الإدراج والتعديل
الكاملة على جدول `app_users`. أُضيف عمودان اختياريان جديدان
(`staff_name`, `staff_email`) لعرض هوية حساب الفريق في الشاشة، لأن الاسم
والبريد الحقيقيين محفوظان فقط داخل `auth.users` غير القابل للقراءة من
التطبيق بدون مفتاح `service_role`.

## قائمة "جميع المسجَّلين" في لوحة المؤشرات

أُضيفت أسفل صناديق لوحة المؤشرات (`/admin`) قائمة كاملة بكل المسجَّلين
بجميع حالاتهم (`app/admin/RegistrantsList.tsx`)، مع إجراءين مباشرين لكل
سجل لم يكن لهما أي واجهة فعلية سابقًا رغم دعم قاعدة البيانات لهما:

- **تعطيل / إعادة تفعيل** — يخفي الملف فورًا من الدليل العام (حالة
  "موقوف")، ويمكن التراجع عنه بالضغط على "إعادة تفعيل" (يعيده إلى حالة
  "معتمد" تحديدًا، لا "منشور" تلقائيًا، ليقرر المراجع النشر من جديد بوعي
  عبر شاشة طلبات الانضمام المعتادة). كان هذا الإجراء موصوفًا في القسم 21
  من الوثيقة دون أي شاشة تنفّذه فعليًا.
- **حذف نهائي مباشر** — يبدأه المدير من هذه القائمة مباشرة (بنفس منطق
  الحذف النهائي في `app/admin/deletion-requests/actions.ts` تمامًا: حذف
  بيانات الهوية/الاتصال/الملف/البيانات المهنية، وقفل تسجيل الدخول عبر
  كلمة مرور عشوائية)، بخلاف تلك الشاشة التي تنتظر طلبًا مسبقًا من صاحب
  الحساب. يظهر تأكيد صريح (`confirm`) قبل التنفيذ نظرًا لعدم إمكانية
  التراجع.

كل الإجراءات مسجَّلة في `audit_logs` (القسم 41)، ومقصورة على `admin` فقط.

> **تحديث:** صناديق لوحة المؤشرات أصبحت صندوقًا مستقلاً **لكل حالة ممكنة**
> (مسودة، طلب جديد، قيد المراجعة، بحاجة استكمال، معتمد، منشور، يحتاج
> تحديثًا، موقوف، مرفوض) بدل 3 فئات مجمّعة فقط، بلون حدّ مختلف لكل حالة
> يطابق ألوان الشارات في القائمة أسفلها. كل صندوق **رابط قابل للضغط**
> (`/admin?status=<الحالة>`) يصفّي قائمة "جميع المسجَّلين" لتعرض فقط تلك
> الحالة — والضغط عليه مجددًا (أو "عرض الكل") يلغي التصفية. التصفية تُقرأ
> من رابط الصفحة نفسه (`useSearchParams`) فتبقى قابلة للمشاركة والرجوع
> إليها مباشرة، دون إعادة جلب البيانات من القاعدة عند كل تبديل.

## مراجعة شاملة للوحة الإدارة وإصلاح أربع ثغرات ذات أولوية عالية

بعد فحص شامل لكل ملفات `app/admin/**` مقابل معايير لوحات الإدارة الاحترافية
(Stripe/Linear/Vercel)، نُفِّذت الإصلاحات الأربعة الأعلى أثرًا فورًا (بقية
الملاحظات — تكرار الكود، حالات التحميل، فشل صامت في معظم `actions.ts`،
اتساق بصري — موثّقة لكن مؤجَّلة):

**1. إعادة هيكلة التنقّل** (`components/AdminNav.tsx` يستبدل الشريط المسطّح
القديم في `app/admin/layout.tsx`):
- شاشات "الطلبات" الأربع (انضمام، تعديل، استعادة حسابات، حذف) مجمَّعة الآن
  تحت قائمة منسدلة واحدة "الطلبات"، بدل تناثرها بين روابط أخرى.
- **شارات عدد للعناصر المعلّقة** لكل شاشة طلبات (وشارة إجمالية على الزر
  الرئيسي) — الأعداد تُحسب في `layout.tsx` بنفس شرط كل شاشة بالضبط.
- تمييز الرابط النشط فعليًا (`usePathname` + `aria-current`)، بدل تساوي كل
  الروابط بصريًا.
- دمج "الإحصائيات" و"التقارير" في رابط واحد "التقارير" (كانا يظهران مرتين:
  في الشريط العلوي وكتبويب فرعي فوق كل منهما).
- درج جوّال (hamburger) للشاشات الضيقة بدل انكسار الشريط على الجوال.
- ترجمة دور الحساب المعروض بجانب زر الخروج (`lib/admin-labels.ts` يوحّد
  `ROLE_LABELS` بدل نسخة محلية كانت في `app/admin/users/page.tsx` فقط).

**2. سدّ ثغرة تجاوز شاشة المراجعة** (`app/admin/RegistrantsList.tsx`):
كان بإمكان المدير تعطيل أو حذف طلب **لم يُراجَع بعد** مباشرة من لوحة
المؤشرات، متجاوزًا شاشة المراجعة الرسمية بإجراءاتها الصحيحة. أصبحت أي حالة
"بانتظار المراجعة" (طلب جديد/قيد المراجعة/بحاجة استكمال) تعرض رابط
"مراجعة الطلب ›" يوجّه لشاشة المراجعة الصحيحة بدل زرّي تعطيل/حذف.

**3. إصلاح منطق الاعتماد/النشر** (`app/admin/applications/actions.ts`
و`[userId]/page.tsx` و`app/admin/actions.ts`):
- حُذف زر "اعتماد دون نشر" لأنه كان يؤدي لنفس نتيجة "اعتماد" تمامًا (لا فرق
  فعلي بينهما) — بقي فقط في قاموس عرض السجل التاريخي للمراجعات القديمة.
- أُضيف إجراء **"نشر"** جديد (`publishAccount`) متاح من قائمة "جميع
  المسجَّلين" لأي حساب بحالة "معتمد" — يسدّ فجوة حقيقية: لم يكن هناك أي
  مسار فعلي لنشر ملف معتمد لاحقًا (شاشة "طلبات الانضمام" تستبعد حالة
  "معتمد" من استعلامها أصلاً).

**4. ثغرات صلاحيات من جهة الخادم** (وليست مجرد إخفاء زر في الواجهة):
- `app/admin/change-requests/actions.ts`: `approveChangeRequest` و
  `rejectChangeRequest` لم يكونا يتحققان من أن الدور فعليًا `admin` —
  أي حساب "مراجع" كان يستطيع استدعاء الإجراء مباشرة وتنفيذه رغم أن الواجهة
  نفسها تصرّح بأن هذا مقصور على المدير.
- `app/admin/password-resets/actions.ts`: `rejectPasswordReset` لم يكن به
  **أي تحقق من الهوية أو الصلاحية إطلاقًا** (بخلاف `resolvePasswordReset`
  المجاورة له في نفس الملف). أُضيف نفس فحص `role === 'admin'`.

## إصلاحان إضافيان من نفس المراجعة: دقة التصدير وتأكيد الإجراءات

**دقة البيانات المصدَّرة** (`app/admin/reports/page.tsx` وتصدير التقارير):
ملف CSV كان يحتوي 3 أعمدة غير ظاهرة على الشاشة إطلاقًا (حساب فيسبوك، نوع
مكان العمل، الموقع) رغم أن تعليق الكود يزعم تطابقًا كاملاً مع الشاشة —
أُضيفت الأعمدة الثلاثة لجدول الشاشة فأصبح التطابق حقيقيًا (19 عمودًا في
الاثنين)، ووُحِّد مسمّى حقل "جهة العمل" (كان يظهر "اسم مكان العمل" في
التصدير فقط لنفس الحقل بالضبط).

**تأكيد متّسق مع خطورة الإجراء الفعلية** (بدل الاعتماد على من كتب كل
شاشة على حدة):
- `components/ToggleSwitch.tsx` (يُستخدم في تعطيل تخصص/فرع/دولة/مدينة):
  أصبح يطلب تأكيدًا صريحًا **فقط عند التعطيل** (لا عند إعادة التفعيل)

## معالجة الفشل الصامت: نظام إشعارات موحّد بدل التجاهل الكامل لأخطاء Supabase

كانت شبه كل ملفات `actions.ts` في لوحة الإدارة تتجاهل قيمة `{ error }`
العائدة من Supabase — فشل صلاحيات RLS أو انقطاع شبكة كان يمر دون أي إشارة
للمستخدم، والحالة الوحيدة التي أظهرت أي شيء عند الفشل كانت `alert()`
المتصفحي البدائي في شاشة واحدة فقط.

**`components/Toast.tsx`** (جديد): إشعار عائم بسيط (نجاح أخضر / خطأ أحمر،
يختفي تلقائيًا بعد 4 ثوانٍ، `aria-live="polite"`) — أول نظام إشعارات موحّد
في المشروع، ليحل محل الصمت الكامل و`alert()` معًا.

عُدِّلت كل الشاشات التالية لترجع `{ok:true} | {error:string}` من كل
Server Action بدل `void`، وتعرض النتيجة عبر `Toast` بدل الصمت:

- **`app/admin/actions.ts`** (تعطيل/نشر/حذف من لوحة المؤشرات) — مربوط في
  `RegistrantsList.tsx`، مع إصلاح وميض "لا يوجد مسجَّلون" أثناء التحميل
  الأول (حالة `loading` صريحة).
- **`app/admin/change-requests`**: أُصلح خطأ سلامة بيانات حقيقي — كان
  الكود يُعلِّم طلب التعديل "معتمد" ويسجّله في `audit_logs` كنجاح حتى لو
  فشل تحديث `profiles`/`professional_profiles` فعليًا. أُضيف أيضًا سجل
  تدقيق للرفض (كان غائبًا بخلاف الاعتماد)، وحُوّلت الصفحة لمكوّن عميل
  (كانت Server Component) لتمكين عرض النتيجة الفعلية.
- **`app/admin/settings`** (تخصصات/فروع/دول ومدن) — كانت **الأسوأ**: لا
  أي تعامل مع الأخطاء إطلاقًا في أربعة ملفات actions. حُوّلت صفحتا الفروع
  والدول/المدن من Server Component إلى مكوّن عميل (لتطابق نمط التخصصات
  أصلاً)، مع رسائل خطأ محدَّدة عند تكرار الاسم (مثل "هذا المجال موجود
  بالفعل" بدل رسالة عامة).
- **`app/admin/password-resets`**: استُبدل `alert()` الوحيد في كل مجلد
  `app/admin` بـ `Toast`، وأُضيف `.eq('status','pending')` على تحديث
  حالة الطلب لمنع معالجته مرتين (نقر مزدوج أو مديران في تبويبين مختلفين).
- **`app/admin/deletion-requests`**: أُصلحت حالة سباق حقيقية — كان الكود
  ينفّذ `setBusyId(null)` **قبل** انتظار اكتمال `load()`، ما يفتح نافذة
  لتنفيذ حذف نهائي مرتين لنفس الطلب؛ الترتيب الصحيح الآن `await load()`
  ثم تحرير الزر. كما استُبدل الاستعلام التسلسلي (2×N طلب لكل صف) باستعلام
  مجمّع واحد، وأُضيف سجل تدقيق للرفض، وبُدِّل الوزن البصري بين زرَّي
  "حذف نهائي" (أصبح مخطَّطًا لا مصمتًا) و"رفض واستعادة" (أصبح الأساسي)
  ليعكس أن الحذف هو الإجراء الأخطر لا الأكثر تفضيلاً.
